## Exact payload and expiry rules

These rows are **bilateral `PerpTrade`** intents for `executeTrade(PerpTrade,bytes,bytes)` (or its batch equivalent), not individually signed `PerpOrderIntent`s. Backend `ExecutionIntent::perp_trade_payload` requires buyerIsMaker, both trader nonces and deadline, rejects non-whole-second `deadline_ms`, and maps `deadline = deadline_ms / 1000` once. Prepare persists `deadline_sec * 1000`; there is no reload fallback that changes the signed deadline. The UUID text is mapped to `intentId = keccak256(UUID UTF-8 bytes)`. Buyer/seller ordering, market, size, execution price, upper/lower price bounds, maker flag, both nonces and deadline occupy the exact 12-field EIP-712 V2 typehash order. Every row supplied all these persisted fields; the complete reconstructed *public* fields, including the bytes32 ID, are in the sanitized [evidence](../artifacts/perps_v2_signed_order_resolution/evidence.json). These bilateral rows have no subaccount or cumulative intent-fill fields.

Frozen PME_V2 `PerpTrade` verifies each declared trader with `ECDSA.tryRecover(digest, signature)`, requires exact bilateral nonces, then advances both nonces on execution. Its deadline predicate is `deadline == 0 || block.timestamp <= deadline`; equality is valid and zero means no expiry. The five disputed rows all have nonzero stored whole-second deadlines before the pinned chain timestamp. For the eight historical-target-verified rows, signature recovery proves the persisted payload (including deadline) was actually signed under that recorded domain. For the five no-target rows, the *stored/reconstructed* deadlines are past, but the signatures do not authenticate the reconstructed payload under the live PME domain or the bounded set of recorded historical targets. Their actual original typed data and signed deadline remain **unproven**. An expired storage field is not, by itself, proof about a different unknown signed payload.

The separate `executeTradeFromIntents` path signs `PerpOrderIntent` fields including trader, subaccount, side, size, limit/bounds, nonce and deadline. Its zero deadline is **not** a no-expiry sentinel: it rejects when current timestamp is greater than zero. First fill consumes `intentNonceUsed`; later partial fills of the *same digest* can continue while `intentFilled[hash] < signed size`, despite the nonce flag. Those rules were not applied to bilateral rows. The empty local nonce/fill ledgers do not prove that no external signed intents exist.
