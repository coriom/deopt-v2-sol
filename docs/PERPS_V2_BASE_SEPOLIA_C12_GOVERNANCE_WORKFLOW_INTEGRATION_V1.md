## Discovery and enforcement boundary

Before this change, no C12 preparation/scheduling/execution adapter existed. The historical `timelock_configuration_manifest.json` remained bound to historical deployment-package/review evidence, while its builder refused regeneration once the corrected V2 manifest was present. `governance_prepare.py`, `governance_execute_prepare.py` and `governance_queue_postflight.py` are pinned earlier G1/G2 recovery tools; they do not handle C12. `recovery_preflight.py` refers to a distinct stranded Engine/Risk topology. The V2 manifest and standalone preflight had no required C12 caller. The old JSON was not executable through a repository C12 adapter because none existed, but an operator could omit the standalone check when planning a manual governance action.

The supported entrypoint is [c12_governance_workflow.py](../tools/perps_v2_cutover/c12_governance_workflow.py). Its CLI takes exactly `--stage`, `--evidence`, and `--output`. It has no `--manifest`, bypass flag, signer, Safe proposal builder, raw transaction builder, or sender. The exact [corrected manifest](../artifacts/perps_v2_replacement_deployment/timelock_configuration_manifest_c12_c20_v2.json) is pinned by SHA-256 `745e7a2fad6a77fef6e35f10a1a431b75615524f51fe13c881c191351ad591fe`. Missing, modified, or historical manifests fail before a PASS record. The prior [blocked review artifact](../artifacts/perps_v2_replacement_deployment/d5_risk_final_review_v2.json) remains unchanged.

Call graph: `main` (lines 95–122) loads evidence, constructs only the read-only RPC client, and calls `require_c12_governance_readiness` (lines 21–92). That function pins the manifest hash, calls [c12_c20_preflight.validate](../tools/perps_v2_cutover/c12_c20_preflight.py) on **every** stage, and then applies the stage-specific boundary. The library verifies Base Sepolia, D4/D5 canonical receipts and runtime, exact C20 Timelock queue/execution events and delay, completed operation state, live D5 owner/Engine/delay 600, D4 Risk zero/migration OPEN, four Engine emergency restrictions, Vault/Insurance non-authorization, unavailable or paused PME, local backend stop, and no unsafe batch. A successful prior check does not replace a fresh check.

## Stage semantics

| Requested stage | Validation and output | Public action |
| --- | --- | --- |
| PREPARE | Fresh authorization-phase preflight; local review evidence only | None |
| REVIEW | Fresh authorization-phase preflight; local review evidence only | None |
| AUTHORIZE | Fresh authorization-phase preflight; includes an earlier-block readback object for later review | No approval granted |
| SCHEDULE | Fresh preflight plus an independently checked earlier authorization readback block and historical Risk/D4 state | No queue call built or sent |
| EXECUTE | Fresh execution-phase preflight; requires separately queued C12 receipt, earlier authorization readback, elapsed Timelock delay and unchanged live state | No execution call built or sent |
| POSTFLIGHT | Explicitly blocked until a separately reviewed public sender/postflight implementation exists | None |

Each successful validation record contains chain and block hash, D4/D5, manifest SHA-256, exact C12 calldata **hash**, C20 operation and receipt references, fresh 600-second readback, and `publicSubmissionEnabled: false`. It is written locally with exclusive creation only after the gate succeeds. The record says `PASS_FOR_SEPARATE_REVIEW_ONLY`; `c12Authorized`, `c12Scheduled`, and `c12Executed` are always false. For example, the future operator may invoke `python tools/perps_v2_cutover/c12_governance_workflow.py --stage authorize --evidence reviewed-c20-public-evidence.json --output new-c12-authorization-readback.json`. This command will currently fail because D5/C20 public state does not exist and D4 maintenance restrictions are not yet active. The output file must be a new path and contains no transaction payload.

For a future SCHEDULE validation, the C20 evidence must include the workflow's earlier `c12AuthorizationReadback` object. The entrypoint verifies that block is canonical, predates the fresh scheduling check, and showed D5 delay 600, D4 Risk zero and migration OPEN. For a future EXECUTE validation, the existing preflight checks that earlier block lies after C20 execution and before C12's separate queue receipt, verifies the queue operation and elapsed Timelock delay, and rechecks current state. Authorization itself remains a separately reviewed human/governance act; no local JSON file proves a Safe approval. A future sender must rerun the execution gate immediately before a one-shot public submission, prohibit automatic retries or fee bumps, treat ambiguous acknowledgement as `SUBMISSION_UNKNOWN`, and reconcile via canonical receipt and storage readback. None of that sender or postflight is implemented or enabled here.
