## Architecture comparison

| Candidate | Result |
| --- | --- |
| A: one native Timelock batch | **Unavailable.** This custom deployed Timelock has `queueTransaction`/`executeTransaction`, not `scheduleBatch`, `executeBatch` or `hashOperationBatch`. Identity is `keccak256(abi.encode(target,value,data,eta))`; there is no predecessor or salt. A single call to MultiSendCallOnly through Timelock fails on the fork; appending setter bytes to `createMarket` succeeds only in creation and leaves the market ACTIVE. |
| B: two Timelock operations, one Safe MultiSendCallOnly execution | **Technically works**, with on-chain atomic revert for that exact Safe transaction. The fork confirms final INACTIVE, ordered execution events and reversal of the creation if the setter fails. However the Safe 2/3 may still invoke either `executeTransaction` individually. A DAG rule cannot remove that ability. |
| New wrapper or D1 upgrade | Would require deployment/authority changes or frozen contract modification outside this mission. No hidden single-operation substitute exists in the deployed path. |

The selected B path is the minimum-change route with currently deployed contracts. V9's separate cancellation of both old operations is unnecessary **if replacement queueing waits until C02 is stale**. The old MKT1 operation can remain queued until its natural expiry, but no authorization to execute it is carried forward. Before market 1 exists it reverts; after the new atomic batch it would only set the already INACTIVE market to INACTIVE again, an unexpected event that should halt downstream governance for review. Cancellation becomes justified if an observed change to executor/Safe authority, a credible separately signed old C02 transaction, or an operator need to schedule before old C02 expiry creates a live overlap. This report requests no cancellation.
